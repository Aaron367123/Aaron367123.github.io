U12 Real-time web app / Data pipeline

Tabletop Campaign Workspace

A real-time workspace for running tabletop role-playing sessions. The game master's screen and every player's phone stay in sync. It has a battle map with fog of war and line of sight, initiative tracking, character sheets computed by a rules engine, a shared dice log and session notes. It's about 66,000 lines of plain JavaScript with no framework and no build step, checked by 4,735 automated checks. For this public edition I also built a data pipeline that keeps only openly licensed rules content, and a licence check that fails the build if anything else gets through.

01 Overview

Running a tabletop campaign means juggling a lot at once: rules, character sheets, initiative order, hit points, a map and dice, spread across the game master's laptop and every player's phone. This app puts all of it in one place and keeps every device up to date live. When the game master damages a goblin, every player sees it straight away. When a player heals, the game master's tracker updates.

Battle map

Tokens sized by creature, fog of war, line of sight that respects walls, rulers and areas of effect. It can find the grid and the walls in an uploaded map picture.

Characters

A step-by-step builder and a full sheet for both the 2014 and 2024 rules. Click any score, save or attack to roll it.

Player phones

Each player gets a phone view with their sheet, the map, the party and notes, and can act on their turn.

Workspace

22 panels as draggable, resizable windows with saved layouts and a command palette. It works offline through a service worker.

02 Sync without clobbering

Every panel saves its state to localStorage, in hundreds of places. Rather than rewrite them all to talk to a server, the sync layer wraps setItem: a write that actually changes a synced key marks it dirty, and dirty keys are pushed to Firebase in one batch 300 ms later.

js/sync/realtime.js
Storage.prototype.setItem = function(key, value) {
  // No-op writes (byte-identical value) neither store nor mark dirty.
  if (TCW_SYNC_KEYS.includes(key) && this.getItem(key) === String(value)) return;
  _orig.call(this, key, value);
  if (!_remoteUpdate && TCW_SYNC_KEYS.includes(key) && _fbDb) {
    _dirtyKeys.add(key);
    clearTimeout(_pushTimer);
    _pushTimer = setTimeout(_flushDirtyKeys, 300);
  }
};

The hard part is two people editing at once. If the whole combat state were saved as one value, the last write would win and wipe out the other change. So combat and the battle map are split into one database node per creature or token: an HP change sends about 200 bytes, and edits to different creatures never collide.

When two devices do change the same record, it goes through a three-way merge against the last version both had seen. Each field is decided separately, and counters like hit points take both changes instead of picking a winner:

js/sync/realtime.js · _merge3
if (baseKnown){
  if (_eq(base, mine))   return theirs;   // we didn't touch it
  if (_eq(base, theirs)) return mine;     // they didn't touch it
}
// ...
// A counter both sides moved (HP, temp HP): apply BOTH changes.
// 30 HP, the DM hits for 10 while the player heals 5: the result is 25.
if (opts && opts.delta && opts.delta.has(k) && inB /* ...all numbers, both changed */){
  let v = theirs[k] + (mine[k] - b[k]);
  if (k === 'hp' && typeof mine.hpMax === 'number'){
    v = Math.min(v, Math.max(mine.hpMax, mine[k], theirs[k]));
  }
  out[k] = Math.max(0, v);
  return;
}

Trimmed. The full merge also handles lists keyed by id (so a reorder on one side doesn't scramble the other), and grouped fields such as a token's x and y, which must come from the same side.

One subtle bug shaped the tie-break. When both sides changed the same field, "my change wins" sounds fair, but each device keeps its own value and re-sends it, forever. Preferring the remote value is the one answer both sides compute identically, so they agree after a single exchange.

03 Do all screens agree?

Each device sends a heartbeat with a signature of what it is showing: which creatures, at what HP, on which squares. If a device disagrees with the others for more than a short grace period, it is marked as behind and gets a Resync button.

My first idea was to hash the stored JSON, but that falsely reported disagreement. Two devices holding the same data can store it in a different key order, because Firebase returns child nodes in its own order. Hashing what is actually on screen measures the thing that matters and nothing else.

04 Rules engine

The character builder stores only the choices a player makes: species, class, level, ability scores, skills, spells and feats. The rules engine turns those choices into the whole sheet: saves, skills, HP, armour class, attacks, spell slots and limited-use resources.

// That is what makes levelling up, changing an earlier choice and switching
// rules edition safe: nothing is accumulated, everything is recomputed.

Because nothing is stored incrementally, levelling down, changing a choice made at level 1, or switching between the 2014 and 2024 rules can't leave stale numbers behind. Features whose effects are only described in prose are handled by small named effect hooks.

05 Open content pipeline

The private version of this app read a large community dataset that includes the full text of published, copyrighted books. To make it public, I had to keep only content released under an open licence: the System Reference Documents (SRD 5.1 and 5.2, CC BY 4.0). This turned into a data migration problem: filter thousands of records across dozens of categories, rewrite the references between them, and prove that nothing protected got through.

A build script keeps only entries marked as SRD, strips lore text, artwork and book references, relabels sources as SRD 5.1/SRD 5.2, and renames 67 entries to their SRD names. There was one catch: the dataset's text comes from the books, not the SRD. So a known list of fixes restores the SRD wording, and any entry that still mentions a protected name is dropped and logged:

tools/build-srd-data.js
return flattenCopies(cat, list, RAW[cat]).map(e => {
  fixReprints(cat, e);
  const c = clean(e, null);   // strip art, lore, book refs; apply SRD wording fixes
  delete c._meta;
  return c;
}).filter(c => {
  const m = PRODUCT_IDENTITY.exec(JSON.stringify(c));
  if (!m) return true;
  DROPPED_PI.push(cat + ': ' + c.name + ' (' + c.source + ') — "' + m[0] + '"');
  if (stats[cat]) stats[cat].after--;
  return false;
});

A separate licence check re-validates the output from scratch, like a reconciliation step after a migration. It checks every data entry's source, scans every text file for lore, art links and protected names, and fails the build if anything is wrong. It runs in CI on every push. While reviewing the output I found that it missed plurals ("mind flayers" got past a pattern for "mind flayer"). I fixed the pattern and added the wording fixes, and the rerun dropped the entries that had slipped through.

06 A demo that can't break anything

The public demo is served from the same site as the private app, so the two share browser storage. Instead of teaching every panel about a demo mode, the demo swaps localStorage itself for a view that reads and writes under its own prefix. The app sees the same API and keys, and a real campaign's data is invisible to it and never written.

js/core/demo.js
const NS = 'tcw-demo:';
const api = {
  getItem: k => real.getItem(NS + k),
  setItem: (k, v) => real.setItem(NS + k, String(v)),
  removeItem: k => real.removeItem(NS + k),
  clear: () => keys().forEach(k => real.removeItem(NS + k)),
  // ...key(i) and length over the namespaced keys only
};

The same switch turns off Firebase and Dropbox, so their SDKs are never even downloaded. An automated check plants a fake real campaign in the browser and loads the demo. It then confirms the campaign is untouched, that the demo wrote only under its prefix, and that none of 124 network requests went to Firebase, Dropbox or an image host.

07 Testing

The self-test suite drives the real app in a headless browser and runs 4,735 checks in four modes: game master (3,629), player (487), mobile (80) and phone (539). Many are regression tests for bugs I hit, such as two devices moving the same token at once and ending up with one device's position and the other's movement count, or an uploaded map turning into an image URL that didn't exist.

  • npm test: the full self-test suite in all four modes.
  • npm run test:demo: 11 checks that the demo is isolated and never syncs.
  • npm run check:licence: 4,049 data entries and 144 text files, all open content.
  • A build stamp content-hashes every asset so the service worker always serves a matching set of files after an update.

08 What I learned

  • Real-time sync is mostly about conflicts. Splitting data into small pieces and merging field by field made "two people editing at once" a normal case instead of a data-loss bug.
  • A merge rule has to converge, not just look fair. "My change wins" on both sides means the two devices argue forever.
  • Making a project public is its own data migration: filter, transform, then independently validate the result, and expect the validation to catch something.
  • Limitations: edits to the same field on two devices still go to one side, and the 2014 rules are thin in the open edition because the SRD includes one subclass per class.
