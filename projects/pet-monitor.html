Smart Pet Monitor

A Raspberry Pi station that sits between a pet's food and water bowls and tracks temperature, the pet's weight, water pH and whether the pet is at the bowl. Readings stream to Firebase every second and show up live in an Android app.

01 Overview

Pet owners can't always be home to see whether their pet is eating, drinking clean water or sitting in a room that's too hot. Our team set out to build a small monitoring station that answers those questions remotely.

The final build is a Raspberry Pi 4 on a custom sensor HAT, housed in a 3D-printed case with two printed bowls. It measures four things and pushes them to the cloud once a second:

Temperature

DHT22 / AM2302 on a GPIO pin, room temperature in °C.

Weight

Interlink force-sensitive resistor read through an ADS1115 ADC.

Water pH

PH-4502C board with a BNC probe in the water bowl, read through the ADC.

Presence (my sensor)

Useful Sensors SEN-21231 Person Sensor over I²C — detects when the pet is at the bowl.

02 My contribution

The project was split so that each of the four team members owned one sensor end-to-end, before we integrated everything onto a shared board and app. I owned the presence-detection sensor:

  • Selected and sourced the SEN-21231 Person Sensor, and put together its bill of materials and project schedule (Gantt chart).
  • Wired it to the Raspberry Pi over the Qwiic / I²C bus and verified it at address 0x62 with i2cdetect.
  • Wrote the Python driver loop that reads raw I²C bytes, unpacks the face-detection results and toggles a status LED on GPIO17, building on the manufacturer's example code.
  • Designed a laser-cut enclosure for the prototype (a CorelDRAW finger-joint box sized around the Pi); the final build moved the sensor into a 3D-printed case on a mounting arm.
  • Presented the working sensor on its own. Its read loop then became the presence section of the team's combined firmware, which publishes faces_detected to Firebase.

03 Hardware

Everything plugs into a single custom HAT designed in KiCad, which stacks onto the Pi's 40-pin header. The analog sensors (force and pH) share one ADS1115 analog-to-digital converter, so the Pi only needs I²C and one GPIO line to talk to all four sensors.

SensorPartInterface
TemperatureDHT22 / AM2302Single-wire, GPIO4
WeightInterlink force-sensitive resistor + 10 kΩADS1115 channel A1 → I²C 0x48
Water pHPH-4502C + BNC electrodeADS1115 channel A0 → I²C 0x48
PresenceSEN-21231 Person SensorQwiic / I²C 0x62

The enclosure went through several iterations: early laser-cut acrylic boxes, then a final set of 3D-printed parts — a Pi case, a sensor case with a mounting arm, a holder for the pH probe and two pet bowls.

04 How it works

The data path is intentionally simple: one Python loop on the Pi reads every sensor and writes the latest value to Firebase, and the app listens for changes.

05 Firmware

The Person Sensor doesn't have a high-level library, so it's read directly from the Linux I²C device. Each read returns a packed binary frame: a header, a face count, then a fixed-size record per face. The integrated firmware unpacks it with struct and reduces it to a single boolean for the app:

firmware/Data.py
try:
    read_bytes = i2c_handle.read(PERSON_SENSOR_RESULT_BYTE_COUNT)
except OSError as error:
    print("No person sensor data found")
    print(error)
    time.sleep(PERSON_SENSOR_DELAY)
    continue
offset = 0
(pad1, pad2, payload_bytes) = struct.unpack_from(
    PERSON_SENSOR_I2C_HEADER_FORMAT, read_bytes, offset)
offset = offset + PERSON_SENSOR_I2C_HEADER_BYTE_COUNT

(num_faces) = struct.unpack_from("B", read_bytes, offset)
num_faces = int(num_faces[0])

faces_detected = num_faces >= 1
db.child("presence").set({"faces_detected": faces_detected})

Excerpt (lightly trimmed) from the integrated loop, which also reads the DHT22 and both ADC channels and writes them with db.child(...).set(...).

06 The app

The Android app, SmartFeeder, uses Firebase Authentication for login and registration, then gives each sensor its own page off a home dashboard. Values update live as the Pi writes new readings.

07 Testing & challenges

Each sensor was tested on its own and then end-to-end through the app:

  • Presence — a pet (and people) in front of the sensor, checking the app flips between found / not eating.
  • Weight — applying pressure to the force sensor and watching the raw reading change.
  • pH — dipping the probe in different liquids.
  • Temperature — moving the unit between environments.
  • App — JUnit tests on the login module and Espresso tests on the navigation drawer.

Problems we hit

  • Getting the Pi talking to Firebase. The first attempts were unreliable; switching to the pyrebase library made writes straightforward.
  • Wi-Fi drop-outs on the Pi, fixed by removing and re-adding the network profile. For the final demo the Pi ran off a phone hotspot.
  • Sharing one I²C bus. Using a single ADC for both analog sensors and Qwiic for the Person Sensor kept every device on distinct addresses (0x48 and 0x62).

Next steps would be calibrating the raw readings into real units (grams and pH instead of ADC values and voltage) and adding the food-dispensing mechanism from the original proposal.

08 What I learned

  • Reading a sensor at the byte level — I²C addressing, binary frame layouts and struct unpacking — rather than relying on a library.
  • The full hardware pipeline: datasheets, BOMs, PCB design in KiCad, laser cutting and 3D printing.
  • How to split a system so four people can build in parallel and still integrate cleanly — clear interfaces (one DB node per sensor) made that possible.
