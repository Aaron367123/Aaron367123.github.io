Multithreaded TCP Command Server

A Java server that accepts telnet connections and runs text commands: word count, time lookup, file inspection and dictionary lookups. It started as a single-threaded, local-only program and grew into a networked server that handles several clients at once with a thread pool, running as a systemd service on Linux.

01 Overview

The goal was to understand what's under every network service: a socket, a simple text protocol, a way to handle many clients at once, and an operating system that keeps it running. The server listens on TCP port 40057. Clients connect with telnet, type a command and get a one-line reply.

Clienttelnet host 40057
ServerSocketaccept() new connection
Thread poolWorker "ClientN" handles the session
DispatchParse line, run command, reply

02 Commands

03 From single-threaded to multithreaded

Version 1: single-threaded, local only

The first version had no networking. It read commands from the console in a loop and dispatched them, with every command stubbed out ("not implemented"). This settled the parsing and dispatch structure before sockets and threads were added.

Version 2: networked, with a thread pool

The final version listens on a ServerSocket and gives each accepted connection to a fixed pool of 3 worker threads from ExecutorService. A pool limits how many threads can exist at once, so a flood of connections can't overload the machine the way "one new thread per client" could.

To make the concurrency visible, each worker renames itself Client1, Client2, … using a synchronized counter, so two threads can never get the same number. Each worker then tells its client which thread and port it's using.

04 Inside the code

The accept loop gives each connection to the pool. The client number is read on the accepting thread, so each worker gets a unique ID:

CmdServer/CmdServer1.java
public synchronized int getNextClientCount(){
    return clientCount++;
}
public void startServer(int port) {
    ExecutorService threadPool = Executors.newFixedThreadPool(3);
    try {
        ServerSocket serverSocket = new ServerSocket(port);
        System.out.println("Server is running and waiting for connections...");

        while (true) {
            Socket clientSocket = serverSocket.accept();
            System.out.println("New client connected.");
            final int currentClient = getNextClientCount();
            threadPool.submit(() -> {
                Thread.currentThread().setName("Client" + currentClient);
                handleClient(clientSocket);
            });
        }

Inside each session, a line is split into a command and its arguments and dispatched with a switch:

CmdServer/CmdServer1.java · handleClient()
String[] tokens = commandLine.split("\\s+");
String command = tokens[0];
String[] commandArgs = new String[tokens.length - 1];
System.arraycopy(tokens, 1, commandArgs, 0, tokens.length - 1);

String result;
switch (command) {
    case "help":  result = help(commandArgs);  break;
    case "count": result = count(commandArgs); break;
    case "time":  result = time(commandArgs);  break;
    case "file":  result = file(commandArgs);  break;
    case "dict":  result = dict(commandArgs);  break;
    default:      result = "no such command";
}
outputStream.write(result.getBytes());
outputStream.write('\n');
outputStream.flush();

Each case was originally on several lines; here they're shortened to one line each.

05 Running it as a Linux service

A server that only runs while someone has an IDE open isn't really a server. I packaged it as a .jar and set it up with systemd:

  • A .service unit runs the jar and sends its output to the system log (syslog).
  • A matching .socket unit declares the server's port (ListenStream=40057) and is enabled under sockets.target.
  • I changed the system's daytime service to run a small C program I wrote. It sets TZ=Asia/Tokyo and replaces itself with /bin/date using execl, so the server's time command returns Tokyo time.
daytime_japan.c
#include <stdlib.h>
#include <stdio.h>
#include <unistd.h>

int main(){
    setenv("TZ", "Asia/Tokyo", 1);
    execl("/bin/date", "date", (char *)NULL);
    perror("execl");
    return 1;
}

06 Testing

  • Concurrency: three telnet clients connected at once and were given threads Client1–3 on separate ports.
  • count: count hello World → Word count: 2.
  • time: returned Tokyo time from the modified daytime service (… JST 2023).
  • file: correct details for a regular file and a directory, and a clear "File does not exist." for a missing file.
  • Service: connected to the systemd-managed server by the VM's IP address, not just localhost.

07 Improvements & lessons

Looking back at the code, here's what I'd change:

  • Handle a client that disconnects without saying Quit. readLine() returns null at end of stream, so the loop should check for that before calling equalsIgnoreCase.
  • Close sockets automatically. Using try-with-resources closes the socket even when an error happens.
  • Allow more clients, or queue them visibly. With 3 workers, a 4th client waits silently. A larger or configurable pool, or a "server busy" message, would be friendlier.
  • Restrict the file command to a safe directory so ../ can't reach outside it, and check the word passed to dict before running the program.

Biggest takeaway: concurrency bugs usually come from shared state. Keeping the only shared value, the client counter, behind one synchronized method made the multithreaded version easy to reason about.
