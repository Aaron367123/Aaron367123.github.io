Myousik 2.0

A full-stack music app: user accounts, a searchable song library, playlists you can build and reorder, and a feedback form. All of it is backed by a REST API and a SQLite database. It's a ground-up rebuild of a static mockup my college team made, which looked like an app but saved nothing.

01 Overview

Version 1 of Myousik was a nice-looking set of static pages. Its "login" and "feedback" forms checked their fields in the browser and then went to a hard-coded "success" page. Nothing was stored. I rebuilt it to work like a real product while keeping the original pink-and-mint brand.

Accounts

Register, log in and log out, with hashed passwords and server-side sessions.

Song library

Full CRUD with search, genre filter, sorting and pagination.

Playlists

Create, rename and delete playlists; add, remove and reorder songs.

Feedback

The original form, now validated on the server and actually saved.

03 Architecture

A deliberately small stack: Express serves both the API and the static front end, and SQLite runs inside the same process using Node's built-in driver. Express is the only runtime dependency. I wrote the cookie parsing, security headers, rate limiter and validation myself, to understand them rather than import them.

04 The API

Every endpoint returns JSON with the right status code, and every error has the same shape ({ error: { code, message, fields } }), so the front end can show the server's field errors next to the right input.

05 Auth & security

  • Passwords are hashed with scrypt and a random salt for each user, and compared in constant time.
  • Sessions use a random token in an httpOnly, SameSite=Lax cookie. The database stores only a hash of the token, so a leaked database can't be used to log in.
  • CSRF protection: requests that change data must be JSON (otherwise 415), and requests from another origin are rejected (403).
  • Rate limiting on login and feedback (429), parameterised SQL everywhere, and security headers on every response.

One detail I'm proud of: logging in with a username that doesn't exist still runs scrypt once, against a dummy hash. Without that, the faster response would reveal which usernames are registered.

src/auth/password.js
export async function verifyPassword(password, saltHex, hashHex) {
  const expected = Buffer.from(hashHex, 'hex');
  const actual = await scryptAsync(normalise(password), Buffer.from(saltHex, 'hex'), expected.length, SCRYPT_OPTIONS);
  // timingSafeEqual throws on length mismatch, so check length first.
  return actual.length === expected.length && timingSafeEqual(actual, expected);
}

/**
 * A throwaway hash used when a login names a user that doesn't exist: we
 * still run scrypt once so the response time doesn't reveal which usernames
 * are registered.
 */
export const DUMMY_CREDENTIALS = await hashPassword(randomBytes(12).toString('hex'));

06 Playlists & reordering

Reordering is easy to get subtly wrong. If two browser tabs edit the same playlist, a stale tab could send an order that drops or duplicates songs. To prevent that, the client sends the complete new order, and the server accepts it only if it contains exactly the playlist's current songs, each once. The new positions are written inside a transaction, so a failure leaves the playlist unchanged.

src/routes/playlists.js
router.put('/:id/songs/order', (req, res) => {
  const playlist = loadOwned(req);
  const { song_ids: newOrder } = check(req.body, schemas.playlistOrder);
  transaction(db, () => {
    const current = orderedSongIds.all(playlist.id).map((r) => r.song_id);
    const sameSet = newOrder.length === current.length && newOrder.every((id) => current.includes(id));
    if (!sameSet) {
      throw badRequest('Order must list every song in the playlist exactly once.', {
        song_ids: 'Must contain exactly the songs currently in the playlist.',
      });
    }
    writeOrder(playlist.id, newOrder);
  });
  res.json(detail(playlist.id));
});

loadOwned returns 404 if the playlist doesn't exist and 403 if it belongs to someone else. The shared validator has already rejected duplicate ids before this code runs.

07 Front end

No framework: each page is an HTML file plus a small JavaScript module, with shared helpers for API calls, forms and the player bar. Forms show errors next to each field and in a summary at the top, announced to screen readers. The layout works down to phone width.

08 Testing

npm test starts the real app on a random port with a fresh in-memory database, then calls it with fetch. That's 37 tests, using only Node's built-in test runner:

  • Auth: register, login, logout, /me, wrong password, duplicate usernames, session expiry.
  • Validation: every write endpoint returns 400 with field errors on bad input.
  • Songs: CRUD, search, sorting and pagination, plus 401 when logged out and 403 when editing someone else's song.
  • Playlists: ownership (403), add, remove and reorder, and rejection of stale or invalid orders.
  • Security: wrong content type (415), cross-origin writes (403) and rate limiting (429).

09 What I learned

  • Client-side validation is for the user's convenience; server-side validation is what keeps data correct. Sharing one module between the two keeps them in sync.
  • Writing my own session handling taught me why libraries do what they do: hashing tokens, constant-time comparison, cookie flags.
  • Test against the real HTTP interface, not internal functions. Those tests caught bugs in middleware order that unit tests wouldn't have.
  • Next steps: password reset, drag-and-drop reordering, shared playlists and a rate limiter that works across multiple servers (for example with Redis).
