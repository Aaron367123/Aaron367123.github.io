01 Overview

The emulator takes MIPS assembly source and runs it on a model of the processor, showing every register and memory change along the way. It's a teaching tool, and a way to prove I understand what happens beneath a compiler.

02 Where it started

Version 1 was a computer-architecture lab series in C. The course provided the text parser. I wrote the simulated memory, the instruction encoders and the CPU's fetch and decode stages, but the labs ended before execution was finished.

I kept v1's design on purpose: the same memory layout, the same course-defined opcodes (for example la = 0x2F and bge = 0x32), and the same bit-packing logic. A test checks the new encoder against the C version's output on 2,000 random inputs.

03 The assembler

Labels can be used before they're defined, so the assembler makes two passes. The first lays out the data section and records each label's address. The second encodes every instruction now that all addresses are known. Each instruction becomes a 32-bit word in one of three formats:

opcode31–26
rs25–21
rt20–16
immediate15–0

I-type (loads, stores, branches, immediates). J-type is opcode + 26-bit address; R-type uses rd, shamt and funct.

Branches store an offset counted from the next instruction, not an absolute address. That's the same calculation as v1's immediate -= (i + 1), written in terms of byte addresses:

src/assembler.js
function branchOffset(token, inst, labels) {
  const target = lookupLabel(token, labels, inst.line);
  const offset = (target - (inst.address + 4)) / 4;
  if (offset < -32768 || offset > 32767) {
    throw new MipsError(`Branch target '${token}' is too far away`, { line: inst.line });
  }
  return offset;
}

Errors such as an unknown instruction, a bad register, a missing label or a misaligned word access are reported with the source line number, and the editor highlights that line.

04 The CPU

The core loop is the four steps from any architecture textbook. The comments link each one to the C function it replaces from v1:

src/cpu.js · step()
const word = this.memory.readWord(pc);  // 1. fetch   (CPU_fetchCode)
this.pc = (pc + 4) >>> 0;               // 2. PC += 4 (PC now points to the next instruction)
const d = decode(word);                 // 3. decode  (CPU_Decode)
this.execute(d, word);                  // 4. execute (CPU_Execution)

Execution is a switch on the decoded instruction. JavaScript numbers aren't 32-bit integers, so the code converts explicitly: >>> 0 for unsigned values and shift tricks for sign extension. Byte loads show it well:

src/cpu.js · execute()
case OPCODE.LB: {
  const byte = this.memory.readByte(this.effectiveAddress(d));
  this.setReg(rt, (byte << 24) >> 24); // sign-extend bit 7
  break;
}
// ...
case OPCODE.BGE:
  if (this.signed(rs) >= this.signed(rt)) this.branch(simm);
  break;

$zero is hard-wired to 0, the program halts on syscall, and system calls 1, 4 and 11 print an integer, a string and a character to the console panel.

05 Bugs I fixed in v1

Finishing the execute stage exposed three bugs in my original design that would have stopped the course program from ever running correctly:

  • la loaded an offset, not an address. v1 stored the data label's offset (e.g. 4) without the 0x2000 base, so the next lw would have read from the code section. It now loads the real address.
  • Decode ignored the function field. Every R-type instruction has opcode 0, so add, sub and slt all looked identical. Decode now reads funct too.
  • Halting on a zero word. v1 stopped when it fetched 0x00000000, but that's a valid instruction (nop). The CPU now halts on syscall or at the end of the code.

I also align .word data to 4 bytes, as standard MIPS assemblers do. In the course program, a one-byte counter left the arrays misaligned, so the first word access would have faulted.

06 Testing

The engine has no UI dependencies, so it's fully tested in Node with the built-in test runner (node --test):

  • Encoder: hand-computed words for each format, plus the 2,000-input comparison with v1's bit layout, and a check that no two instructions share an encoding.
  • Assembler: labels used before they're defined, PC-relative branches in both directions, directives, alignment and error line numbers.
  • Memory: little-endian byte order and misaligned-access errors.
  • CPU: the result of each instruction, including overflow, sign extension and hi/lo.
  • End-to-end: the original course program runs unchanged and the two arrays come out swapped, plus factorial (recursion with jal/jr and the stack), array sum and string length.

07 What I learned

  • Finishing a design is the real test of it. All three v1 bugs only showed up once the execute stage existed.
  • Keeping the engine free of UI code made it easy to test thoroughly, and let the same code power both a command-line tool and the browser.
  • Integer behaviour depends on the language: C gives you 32-bit arithmetic, but JavaScript needs explicit conversions to get the same results.
  • Next steps: a pipelined mode that shows hazards and forwarding, and the missing lh/sh/jalr instructions.
