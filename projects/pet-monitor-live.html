01 Overview

In the capstone, a Raspberry Pi pushed four raw readings to Firebase every second, and the Android app showed only the latest numbers. The weight was a raw ADC count, the pH was a voltage, and there was no history, no charts and no alerts. Pet Monitor Live adds the layer in between:

Capstone (v1)

Team of 4 · Fall 2023 – Winter 2024
  • 4 sensors on a custom Pi HAT
  • Latest value per sensor in Firebase
  • Raw ADC counts and volts, not grams or pH
  • No history, charts or alerts
  • No offline handling

Pet Monitor Live

Solo extension
  • Validated, authenticated ingest API
  • Two-point calibration to grams and pH
  • Visit detection: eating vs drinking
  • Alerts with hysteresis, cooldown and fault detection
  • History, live charts, offline buffering on the Pi

03 Calibration

Sensors report voltages and counts, not grams or pH. Both conversions use a two-point linear calibration: measure two known reference points, and every other reading falls on the straight line between them.

Weight (force-sensitive resistor)

Read the empty bowl (tare) and a known mass, then: grams = (raw − tareRaw) × knownMass ÷ (knownRaw − tareRaw). A force-sensitive resistor isn't truly linear, so this is an approximation over the bowl's working range. A load cell would be the hardware upgrade.

Water pH (PH-4502C)

Dip the probe in pH 7 and pH 4 buffer solutions and record their voltages (about 2.50 V and 3.04 V). Then slope = 3 ÷ (V₇ − V₄) and pH = 7 + (V − V₇) × slope. An optional correction adjusts the slope for water temperature (the Nernst equation), because pH probes respond differently when warm or cold.

04 Visit detection

The Person Sensor (the part I built in the capstone) only says "face present: yes or no", once a second. A small state machine turns that into visits. A visit starts after several readings in a row see the pet, and ends after several in a row don't, so one noisy reading can't split a visit in two. When the pet leaves, the bowl weight is compared with its weight before the visit to decide whether the pet was eating or drinking:

shared/sessions.js
// Confirmed departure; the visit ended at the last reading that saw the pet.
const { startTs, lastSeenTs, baselineG } = this.current;
const afterG = median(this.leaving.map((x) => x.weightG));
const foodEatenG = baselineG != null && afterG != null ? round(Math.max(0, baselineG - afterG), 1) : null;
const kind = foodEatenG != null && foodEatenG >= minEatenG ? 'eating' : 'drinking';
const event = {
  type: 'visit_end',
  ts: r.ts,
  startTs,
  endTs: lastSeenTs,
  durationS: Math.round((lastSeenTs - startTs) / 1000),
  kind,
  foodEatenG,
  // ...
};

Taking the median weight after the pet leaves makes the "food eaten" estimate robust to the bowl wobbling.

05 Alerts without false alarms

A simple if (temp > 30) alert() fires dozens of times as a reading jitters around 30.0. Each alert rule here uses three techniques:

  • Confirmation: the condition must hold for N readings in a row before the alert fires.
  • Hysteresis: an alert that fired at 30 °C clears only below 29 °C, so a value hovering at the limit doesn't flicker on and off.
  • Cooldown: a resolved alert can't fire again straight away.
shared/alerts.js · AlertTracker.update()
update(ts, triggered, cleared, { confirm = 1, cooldownMs = 0 } = {}) {
  if (!this.active) {
    this.pending = triggered ? this.pending + 1 : 0;
    const coolingDown = this.lastFiredAt != null && ts - this.lastFiredAt < cooldownMs;
    if (this.pending >= confirm && !coolingDown) {
      this.active = true;
      this.pending = 0;
      this.lastFiredAt = ts;
      return 'fire';
    }
    return null;
  }
  if (cleared) {
    this.active = false;
    return 'resolve';
  }
  return null;
}
AlertDefault rule
Room temperatureAbove 30 °C or below 15 °C, ±1 °C hysteresis
Water pHBelow 6.5 or above 8.5, ±0.2 hysteresis
No visitThe pet hasn't been to the bowl for 8 hours
Device offlineNo reading for 10 seconds
Sensor faultStuck value, a spike compared with the median of the last 5 readings, out of range, or missing

Readings flagged as faulty are kept out of the charts and the threshold alerts. Otherwise one bad temperature reading of 62 °C would also fire a "room too hot" alert.

06 Real-time streaming

New dashboard connections first receive a full snapshot, then live updates. A browser on a slow connection mustn't make the server queue up unlimited data, so readings are skipped for a client that has fallen behind. Alerts and events, which matter more, are always sent:

server/ws.js
function broadcast(msg) {
  if (wss.clients.size === 0) return;
  const payload = JSON.stringify(msg);
  const droppable = msg.type === 'reading';
  for (const ws of wss.clients) {
    if (ws.readyState !== WebSocket.OPEN) continue;
    if (droppable && ws.bufferedAmount > maxBufferedBytes) {
      ws.dropped++;
      continue;
    }
    ws.send(payload);
  }
}

The dashboard reconnects automatically with increasing delays (backoff), and a heartbeat message lets both sides notice a dead connection.

07 Testing

52 tests with Node's built-in test runner. Because the logic is made of pure functions, most tests just feed in timestamped readings and check what comes out:

  • Calibration maths, including the temperature correction and rejection of invalid calibration values.
  • Alerts: confirmation counts, hysteresis bands, cooldowns and fault detection.
  • Visits: debouncing, eating vs drinking, and daily totals.
  • Validation of ingest and configuration, and history bucketing.
  • Integration: boots the real server with an in-memory database, posts readings over HTTP and checks that a WebSocket client receives the reading and alert messages.

The Python Pi client was tested in --mock mode against the live server. Its real-hardware mode uses the same sensor code as the capstone firmware, but hasn't been run on a Pi yet.

08 What I learned

  • Raw sensor data is only useful after calibration, filtering and context. Most of the work sits between the sensor and the screen.
  • Hysteresis and confirmation are what make alerts trustworthy. A noisy alert gets muted and then ignored.
  • Keeping logic free of I/O paid off three times: easy tests, a server and a browser demo from one codebase, and a simulator to develop against without hardware.
  • Next steps: run it on the real Pi, replace the force-sensitive resistor with a load cell, add push notifications, and support several devices per user.
