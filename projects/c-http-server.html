tinyhttpd: an HTTP server in C

A multithreaded HTTP/1.1 static-file server written from scratch in C, with no libraries beyond the OS. It has a bounded work queue with back-pressure, keep-alive and pipelining, defences against path traversal, and graceful shutdown. I also wrote a load-testing tool in C and used it to measure how the design scales.

01 Overview

My Java command server taught me sockets and thread pools, with Java taking care of the hard parts. This project removes that help. In C I had to manage every buffer, every lock and every way a connection can fail, and then measure whether the design holds up under load.

HTTP/1.1

GET/HEAD, keep-alive, pipelining, HTTP/1.0, If-Modified-Since → 304, correct error codes.

Bounded concurrency

A fixed pool of worker threads plus a bounded queue. When it's full, the server answers 503 instead of slowing down.

Hardened file serving

Blocks 11 path-traversal tricks, hidden files and Windows device names. Files are sent in chunks.

Graceful shutdown

Ctrl-C stops accepting, drains the queue, joins the workers and prints statistics.

It runs on Windows (Winsock) and Linux/macOS (POSIX sockets) from one codebase. Every #ifdef _WIN32 sits in two small compatibility files (net.c and platform.c), so the server logic never touches OS-specific code. Request counters use C11 atomics, and access-log lines are written under a mutex so lines from different threads never interleave.

03 The work queue

Creating a thread for every connection collapses under a traffic spike. Instead, the accept thread puts connections into a fixed-size ring buffer, and a fixed number of workers take them out. Two condition variables coordinate them: not_empty wakes a worker and not_full wakes a producer.

src/queue.c
int queue_try_push(queue_t *q, const job_t *job)
{
    int rc;
    pthread_mutex_lock(&q->mu);
    if (q->closed) {
        rc = -1;
    } else if (q->count == q->capacity) {
        rc = 0; /* full: caller applies back-pressure (503) */
    } else {
        enqueue_locked(q, job);
        rc = 1;
    }
    pthread_mutex_unlock(&q->mu);
    return rc;
}

int queue_pop(queue_t *q, job_t *out)
{
    int rc = 0;
    pthread_mutex_lock(&q->mu);
    while (q->count == 0 && !q->closed)
        pthread_cond_wait(&q->not_empty, &q->mu);
    if (q->count > 0) { /* closed queues still hand out what is left */
        *out = q->items[q->head];
        q->head = (q->head + 1) % q->capacity;
        q->count--;
        pthread_cond_signal(&q->not_full); /* one slot freed -> wake one producer */
        rc = 1;
    }
    pthread_mutex_unlock(&q->mu);
    return rc;
}
  • The wait is inside a while, not an if, because condition variables can wake up spuriously.
  • The accept thread uses the try version: when the queue is full it replies 503 immediately instead of blocking. That's back-pressure.
  • For shutdown, the queue is closed but still hands out jobs already in it, so requests that were accepted get finished.

04 Speaking HTTP

The parser enforces strict limits: 8 KB of headers (431), maximum URI length (414), unsupported versions (505) and malformed request lines (400). Each worker then runs a keep-alive loop on its connection. The fiddly part is what happens after each response:

src/conn.c
if (io_err || !keep) {
    /* Unread input (error, or pipelined requests we won't serve)
     * would turn our close into a RST: drain it first. */
    linger = !io_err && (status >= 400 || (size_t)hdr_len < used);
    break;
}
/* Keep-alive: slide any pipelined bytes to the front of the buffer. */
used -= (size_t)hdr_len;
memmove(b->rx, b->rx + hdr_len, used);

Two subtle things are handled here. If a client sent several requests at once (pipelining), the leftover bytes are the start of the next request, so they're moved to the front of the buffer. And closing a socket that still has unread data makes the OS send a reset (RST), which can wipe out an error response before the client reads it. So the server drains the remaining input before closing (a "lingering close").

05 Path traversal

The classic static-server bug is GET /../../secret. Attackers disguise it with encodings like %2e%2e/, backslashes, or Windows quirks. My rule: decode first, then check every path segment, and reject anything unusual rather than trying to clean it up:

src/fileserve.c
static int segment_ok(const char *seg, size_t n)
{
    size_t i;
    if (seg[0] == '.')
        return 0; /* "..", and hidden files such as .git or .env */
    if (seg[n - 1] == '.' || seg[n - 1] == ' ')
        return 0; /* Windows silently strips these: "index.html." == "index.html" */
    for (i = 0; i < n; i++) {
        unsigned char c = (unsigned char)seg[i];
        if (c < 0x20 || c == 0x7f)
            return 0; /* control characters */
        if (strchr("\\:*?\"<>|", c) != NULL)
            return 0; /* '\' is a separator on Windows; ':' = drives/streams; wildcards */
    }
    return !is_device_name(seg, n);
}

The integration tests try 11 variants (encoded dots, mixed separators, NUL bytes, trailing dots, device names like CON), and every one gets a 403.

06 Testing

  • 163 unit checks in a small C test runner: the parser, percent-decoding, the path checks, MIME types, and the queue under several threads at once.
  • 21 integration tests (Python standard library only) start the real server and send real requests: status codes, HEAD, 304s, keep-alive, pipelining, HTTP/1.0, idle timeout, 50 parallel clients, 503 back-pressure and graceful shutdown.
  • The build runs with warnings treated as errors, and cppcheck, a static analyser, reports nothing.
  • A GitHub Actions workflow is set up to build and test on Ubuntu (including AddressSanitizer and UndefinedBehaviorSanitizer, which catch memory bugs) and on Windows. So far everything has been built and tested on Windows only.

What the numbers say

  • Keep-alive adds up to 67% throughput. Without it, every request pays for a new TCP handshake, and that cost dominates for small files.
  • Diminishing returns after 4 workers, which matches the 4 physical cores. The benchmark client competes for the same CPU.
  • The design's weak spot shows up in the worst-case latency. With keep-alive, a worker stays with one connection until it closes. With 32 connections and fewer workers, connections wait their turn, so p99 latency reaches 96–441 ms while the median stays under 1 ms. A simple queueing model predicted the worst case to within 10% (710 ms predicted vs 771 ms measured with 1 worker).

That tail latency is why production servers like nginx use an event loop (epoll/IOCP), where one thread juggles many idle connections. It's the clear next step for this project.

08 What I learned

  • Condition variables, wake-up order and shutdown coordination are where concurrency bugs hide. Testing the queue with many threads at once was worth it.
  • The network has many edge cases: partial reads, pipelined bytes, resets when closing with unread data, and clients that send nothing at all.
  • Security in file paths comes from rejecting anything unexpected, not from trying to clean it up.
  • Measure, then explain. The benchmarks showed exactly where the thread-per-connection design breaks down, which tells me what to build next.
