01 Overview

PID controllers keep drones level, motors at speed and ovens at temperature. Their equation fits on one line, but the version that works on real hardware needs several extra details: saturation, integral windup, derivative kick and sensor noise. I built this lab to understand those details by changing them and watching what happens.

The simulation is deterministic: the same settings always give the same result, whatever the screen's frame rate. That's why the live metrics match the offline test numbers exactly.

02 What P, I and D each do

The quadcopter shows it best. Gravity pulls constantly, so the drone needs a steady thrust just to hover:

  • P reacts to the present error. On its own it can't hold the drone up without some error left over, so it settles about 1.7 m short of the target.
  • + I accumulates past error until that offset is gone. But the extra lag makes the loop less stable, and the oscillation grows.
  • + D reacts to how fast the measurement is changing and adds damping: 0.87% overshoot, settled in 2.85 s.

03 A real-world PID

A textbook PID behaves badly on real hardware. Each fix below is a switch in the lab, so you can turn it off and see the problem it solves:

  • Derivative on measurement: a setpoint step makes the error jump instantly, which spikes the D term (a "derivative kick"). Differentiating the measurement instead avoids it.
  • Derivative filter: D amplifies sensor noise, so a first-order low-pass filter (time constant Td/N) smooths it.
  • Anti-windup: when the actuator is maxed out, the integral keeps growing and causes a big overshoot later. Clamping stops the integral while saturated. Back-calculation bleeds off the excess.
  • Output limits, setpoint weighting and bumpless gain changes round it out.

04 The plants

Each plant is a set of differential equations solved with 4th-order Runge–Kutta (RK4) at a 1 ms internal step, separate from the controller's sample time. That way, slowing the controller down never makes the physics less accurate.

src/plants.js
export function rk4Step(f, x, h) {
  const n = x.length;
  const tmp = new Array(n);
  const k1 = f(x);
  for (let i = 0; i < n; i++) tmp[i] = x[i] + 0.5 * h * k1[i];
  const k2 = f(tmp);
  for (let i = 0; i < n; i++) tmp[i] = x[i] + 0.5 * h * k2[i];
  const k3 = f(tmp);
  for (let i = 0; i < n; i++) tmp[i] = x[i] + h * k3[i];
  const k4 = f(tmp);
  const out = new Array(n);
  for (let i = 0; i < n; i++) out[i] = x[i] + (h / 6) * (k1[i] + 2 * k2[i] + 2 * k3[i] + k4[i]);
  return out;
}

A test checks RK4 against the exact solution of a first-order system: the error stays below 10⁻⁶.

05 Relay autotuning

The Ziegler–Nichols method needs the plant's ultimate gain Ku and period Tu: the gain at which the loop oscillates steadily, and the period of that oscillation. Pushing a real machine to the edge of instability is risky, so the Åström–Hägglund relay method gets the same numbers safely. The controller is swapped for an on/off relay, the plant settles into a small steady oscillation, and Ku and Tu are measured from it.

src/tuning.js · relay step
step(r, y, t) {
  const e = r - y;
  const prev = this.high;
  if (this.high === null) this.high = e >= 0;
  else if (e > this.eps) this.high = true;      // hysteresis band
  else if (e < -this.eps) this.high = false;

  if (prev === false && this.high) this.onUp(t);
  if (prev === true && !this.high) this.downs.push(t);

  const u = Math.min(this.uMax, Math.max(this.uMin, this.bias + (this.high ? this.h : -this.h)));
  this.log.push({ t, u, y });
  if (this.ups.length > this.cycles) this.done = true;
  return u;
}

The textbook formula estimates Ku from the oscillation's peak height. On the heater, the time delay distorts the waveform and that estimate was 20% off. Using only the oscillation's fundamental frequency component (a single-frequency Fourier estimate, Ku = |U₁| / |Y₁|) brought it within 2%:

06 The C library

The simulator proves the maths; the C library is what you'd actually flash to a microcontroller. It's C99 with no dynamic memory and the same features as the JavaScript version, behind a small init/update/reset API. Here's the heart of the update step:

firmware/pid.c
/* Filtered derivative (backward Euler): D[k] = Tf/(Tf+Ts)*D[k-1] + Kd/(Tf+Ts)*(ed[k]-ed[k-1]) */
d = (c->tf / (c->tf + c->ts)) * pid->deriv + (c->kd / (c->tf + c->ts)) * (ed - pid->ed_prev);

/* Output and saturation */
v = p + pid->integ + d;
u = clampr(v, c->out_min, c->out_max);
sat = (v > c->out_max) ? 1 : ((v < c->out_min) ? -1 : 0);

/* Integrator update for the next sample, with anti-windup */
d_integ = c->ki * c->ts * e;
if (c->aw == PID_AW_CLAMP) {
    /* Conditional integration: hold I while saturated and e drives deeper into the limit */
    if ((sat > 0 && e > (pid_real_t)0) || (sat < 0 && e < (pid_real_t)0)) {
        d_integ = (pid_real_t)0;
    }
} else if (c->aw == PID_AW_BACKCALC) {
    /* Back-calculation: feed the saturation excess (u - v) back with gain 1/Tt */
    d_integ += (c->ts / tracking_time(c)) * (u - v);
}

Proving C matches JavaScript

A script records three closed-loop runs from the JavaScript model as "golden" CSV files: 1,300 samples covering every anti-windup mode, gain changes, a reset, noise and quantisation. The C tests replay the same inputs and compare every output.

07 What I learned

  • The PID equation is the easy part. Saturation, windup, noise and sample delay decide whether it works on real hardware.
  • Keep the physics' time step separate from the controller's sample rate, and the simulation stays accurate and repeatable.
  • Check numbers against what you can measure. The textbook relay formula was 20% off on a delayed plant, and the tests caught it.
  • Golden-file tests are a simple, strong way to keep two implementations in different languages in sync.
  • Next steps: flash it to a real motor rig, add feed-forward and gain scheduling, and fix the rate limiter so it feeds back into the anti-windup.
